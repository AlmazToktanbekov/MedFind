## 1. ВВЕДЕНИЕ

### 1.1. Краткое описание

**MedFind** — мобильное приложение для Кыргызстана, объединяющее в одной платформе врачей, медицинские клиники и аптеки. Пациенты получают единый удобный канал для поиска медицинских услуг, а медицинские учреждения — инструмент для привлечения новых клиентов и управления своим профилем.

### 1.2. Проблема, которую решает приложение

На текущий момент в Кыргызстане:
- Информация о медицинских специалистах разрозненна (Instagram, 2GIS, сарафанное радио)
- Отсутствует единый источник проверенной информации о врачах
- Пациенту сложно заранее узнать цены, график работы, специализацию врача
- Клиники и аптеки не имеют удобного цифрового канала для работы с клиентами кроме социальных сетей

### 1.3. Предлагаемое решение

Платформа-агрегатор медицинских услуг с тремя ключевыми отличиями от конкурентов:

1. **Система верификации врачей через клиники** — врач не виден пациентам, пока клиника не подтвердит его профиль (статус `active`). Это создаёт доверие.
2. **Прямая связь с врачом/клиникой** через WhatsApp, Telegram, телефонный звонок (без посредников и комиссий).
3. **Поддержка трёх языков**: русский (`ru`), кыргызский (`ky`), английский (`en`).

## 2. ЦЕЛИ И ЗАДАЧИ ПРОЕКТА

### 2.1. Главная цель

Создать рабочее мобильное приложение и серверную часть, объединяющие пациентов, врачей, клиники и аптеки в одну экосистему, с реалистичной бизнес-моделью монетизации.

### 2.2. Технические задачи

1. Разработать кроссплатформенное мобильное приложение (iOS + Android) на Flutter
2. Реализовать REST API серверную часть на FastAPI с асинхронной работой с базой данных
3. Спроектировать реляционную модель данных в PostgreSQL
4. Реализовать многоязычность интерфейса
5. Внедрить систему JWT-аутентификации с автообновлением токенов
6. Создать систему ролей (пациент, врач, клиника, аптека, администратор)
7. Реализовать веб-административную панель
8. Внедрить аналитику действий пользователей
9. Разработать систему монетизации через личные счета и подписки

### 2.3. Образовательные задачи

В рамках выполнения дипломного проекта были изучены и применены:
- Архитектурный паттерн **Layered Architecture** (data → providers → presentation)
- Реактивное управление состоянием (**Riverpod** для Flutter)
- Асинхронное программирование на Python (`asyncio`, `asyncpg`)
- Object-Relational Mapping (**SQLAlchemy 2.0** в async-режиме)
- Управление миграциями БД (**Alembic**)
- Декларативная навигация (**GoRouter**)
- Аутентификация и авторизация (**JWT**, refresh tokens)
- Push-уведомления (**Firebase Cloud Messaging**)
- Кэширование и оптимистические обновления
- Принципы безопасной разработки (rate limiting, защита от SQL-инъекций, hash паролей с bcrypt)

## 4. БИЗНЕС-МОДЕЛЬ

### 4.1. Подход

Используется модель **B2B2C** (Business-to-Business-to-Consumer):

```
ПАЦИЕНТ (бесплатно)  ←  КЛИНИКА/АПТЕКА (платит)  →  MedFind
```

Пациенты не платят за пользование приложением — они являются трафиком, который монетизируется через клиник и аптеки.

### 4.2. Тарифные планы

Тарифы одинаковы для клиник и аптек:

| Параметр | **Free** | **Pro** | **Premium** |
|----------|----------|---------|-------------|
| Цена в месяц (USD) | $0 | $20 | $40 |
| Цена в год (USD) | $0 | $200 (экономия $40) | $400 (экономия $80) |
| Максимум врачей (для клиник) | 4 | ∞ | ∞ |
| Максимум филиалов (для аптек) | 9 | ∞ | ∞ |
| Карточка профиля | ✅ | ✅ | ✅ |
| Раздел «Отчёты» (аналитика) | ❌ | ❌ | ✅ |
| Бейдж «Премиум / Рекомендуем» | ❌ | ❌ | ✅ |
| Приоритет в поиске | ❌ | ❌ | ✅ |

### 4.3. Триальный период

При регистрации клиники или аптеки автоматически активируется **Pro-план на 30 дней бесплатно** (`is_trial=true`). Триал даётся **только один раз навсегда** на сущность.

### 4.4. Механизм оплаты — личный счёт (кошелёк)

Использована модель **B2B-счёта**, аналогичная Google Ads, Booking.com:

1. У каждой клиники/аптеки есть **кошелёк** в USD
2. Пополнение происходит через банковский перевод на расчётный счёт MedFind
3. При создании заявки на пополнение генерируется **уникальный код платежа** вида `MEDF-31-A7K4`, который клиника обязана указать в назначении банковского перевода
4. Администратор сверяет код с банковской выпиской и подтверждает зачисление
5. При покупке подписки сумма списывается с баланса (атомарная транзакция с `SELECT FOR UPDATE`)

**Безопасность:** Платёжные карты пользователей не хранятся, прямая интеграция с банковским API не требуется.

**Масштабируемость:** Архитектура реализована через паттерн **Strategy** (`WALLET_CONFIRM_STRATEGY`). Текущая стратегия — `manual` (ручное подтверждение). При получении API Mbank Business достаточно переключения на стратегию `mbank_auto` без изменения остального кода. Endpoint-заглушка для webhook'а банка уже реализована.

## 5. АНАЛИЗ КОНКУРЕНТОВ

### 5.1. Обзор рынка

На момент разработки проекта в Кыргызстане **отсутствует специализированное мобильное приложение-агрегатор медицинских услуг**. Информация о врачах и клиниках распределена по нескольким каналам, каждый из которых имеет существенные ограничения.

### 5.2. Прямые и косвенные конкуренты

#### 5.2.1. **2GIS Кыргызстан**

- **Тип:** Городской справочник и навигатор
- **Сильные стороны:**
  - Высокий охват аудитории
  - Качественные карты и маршруты
  - Информация о графике работы организаций
- **Слабые стороны:**
  - Не специализирован на медицине — клиника отображается как «обычная организация»
  - Нет системы верификации врачей
  - Нет рейтингов и отзывов на отдельных специалистов
  - Невозможно фильтровать по симптомам, специализациям, формату консультации
  - Нет личных кабинетов для медицинских учреждений

#### 5.2.2. **Namba Doctor**

- **Тип:** Сервис онлайн-консультаций
- **Сильные стороны:**
  - Видеосвязь с врачом внутри платформы
  - Хорошая узнаваемость бренда (Namba)
- **Слабые стороны:**
  - **Только онлайн-консультации** — не помогает найти врача для офлайн-приёма
  - **Высокая цена** консультации (~700-2000 сом)
  - Малое количество специалистов
  - Нет каталога клиник и аптек
  - Закрытая монолитная модель без подписок для клиник

#### 5.2.3. **Instagram / WhatsApp-каналы врачей**

- **Тип:** Социальные сети как основной канал привлечения пациентов
- **Сильные стороны:**
  - Бесплатно для врача и пациента
  - Прямая коммуникация
  - Привычность для пользователей
- **Слабые стороны:**
  - **Нет верификации** — невозможно проверить наличие диплома
  - Нет рейтингов
  - Нет фильтров и поиска
  - Информация хаотична
  - Зависимость от алгоритмов соцсетей

#### 5.2.4. **Сайты медицинских клиник**

- **Слабые стороны:**
  - У каждой клиники свой сайт — нет единой точки входа
  - Часто устаревший контент
  - Нет мобильной адаптации
  - Невозможно сравнить клиники между собой

#### 5.2.5. **Российские аналоги (DocDoc, ПроДокторов)**

- **Не работают в Кыргызстане** — географическое ограничение
- Используются как референс по UX и функциональности

### 5.4. Уникальное торговое предложение (USP)

> **MedFind — единственное в Кыргызстане приложение, объединяющее врачей, клиники и аптеки в одной системе, где каждый специалист подтверждён реальной клиникой, а связь с ним происходит за один клик через привычный мессенджер.**

Ключевые отличия:

1. **Система доверия:** статус `active` врача означает что клиника подтвердила его профиль
2. **Без посредников:** пациент звонит/пишет напрямую — комиссия с консультаций не взимается
3. **Доступная цена для бизнеса:** Pro $20/мес — в 5-10 раз дешевле рекламы в Instagram
4. **Прозрачность для клиник:** Premium-аналитика показывает источники трафика и эффективность

### 5.5. Барьеры для входа конкурентов

1. **Сетевой эффект:** чем больше клиник и врачей в системе, тем выше ценность для пациентов
2. **Локальные особенности:** интеграция с местными SMS-сервисами (Nikita.kg), картами (2GIS), языками
3. **Доверие клиник:** установление партнёрских отношений требует времени
4. **Накопленные отзывы:** база отзывов — серьёзный актив, который нельзя быстро воспроизвести

### 6.4. Расчёт юнит-экономики

#### 6.4.1. Стоимость привлечения клиента (CAC)

Для привлечения одной клиники:

| Канал | Стоимость на клинику |
|-------|----------------------|
| Прямые продажи (звонки, встречи) | ~$30 |
| Реклама в Instagram (taргетинг на владельцев) | ~$20 |
| Конференции, мероприятия | ~$15 |
| Реферальная программа (бонус приведшему) | ~$15 |
| **Итого средний CAC** | **~$50** |

#### 6.4.2. Пожизненная ценность клиента (LTV)

Расчёт LTV для клиники на тарифе Pro:

- Средний период удержания (retention): **24 месяца**
- Месячная подписка: **$20**
- Вероятность апгрейда на Premium: **~20%**

**Формула LTV:**
```
LTV = (Средний чек × Срок удержания) + Доп. услуги
    = ($20 × 24 мес.) × 0.8 + ($40 × 24 мес.) × 0.2
    = $384 + $192
    = $576
```

**С учётом косвенных доходов** (платное продвижение, реклама) реальный LTV выше — около **$720**.

#### 6.4.3. Соотношение LTV/CAC

```
LTV / CAC = $720 / $50 = 14.4
```

**Норма для здорового SaaS-бизнеса:** LTV/CAC ≥ 3.

**Показатель MedFind = 14.4** свидетельствует об **очень эффективной юнит-экономике**. Каждый доллар, вложенный в привлечение клиента, возвращается в 14-кратном размере.

### 5.1. Общая схема

```
┌─────────────────────────────────────────────────────────────┐
│                  МОБИЛЬНОЕ ПРИЛОЖЕНИЕ                       │
│                       (Flutter)                             │

└─────────────────────────┬───────────────────────────────────┘
                          │ HTTPS + JWT
                          ▼
┌─────────────────────────────────────────────────────────────┐
│                    BACKEND API                              │
│                    (FastAPI / Python)                       │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Routers       (FastAPI endpoints)                   │   │
│  │  Services      (Бизнес-логика)                       │   │
│  │  Models        (SQLAlchemy ORM)                      │   │
│  │  Schemas       (Pydantic validation)                 │   │
│  └──────────────────────────────────────────────────────┘   │
└─────┬──────────────────────────────────┬────────────────────┘
      │                                  │
      ▼                                  ▼
┌──────────────┐                ┌─────────────────────┐
│  PostgreSQL  │                │  Внешние сервисы:   │
│  (asyncpg)   │                │  • Firebase FCM     │
│              │                │  • Nikita.kg SMS    │
└──────────────┘                │  • Mistral AI       │
                                └─────────────────────┘
```

### 5.2. Архитектура мобильного приложения (Flutter)

Каждая функциональная область (`feature`) разделена на 3 слоя:

- **`data/`** — `Repository`-классы делают HTTP-запросы через единый `ApiClient`, возвращают модели предметной области
- **`providers/`** — `StateNotifierProvider` (Riverpod) содержит бизнес-логику и состояние
- **`presentation/screens/`** — Flutter-виджеты, читают данные через `ref.watch` / `ref.read`

**Реализованные фичи** (15 модулей):
`ai`, `analytics`, `auth`, `clinics`, `doctors`, `health`, `home`, `notifications`, `pharmacies`, `profile`, `provider`, `search`, `subscription`, `wallet`

### 5.3. Архитектура серверной части (Backend)

- **Асинхронная SQLAlchemy** с драйвером `asyncpg`
- **Зависимость `Depends(get_db)`** обеспечивает изолированную сессию БД на каждый запрос
- **Eager loading** связанных сущностей через `selectinload` (избегаем N+1 проблемы)
- **Pydantic-схемы**: отдельные классы для чтения (`DoctorOut`, `ClinicOut`) и записи (`DoctorCreate`, `ClinicUpdate`)
- **Pydantic-settings** для конфигурации (загрузка из `.env`)

## 12. БЕЗОПАСНОСТЬ

### 10.1. Аутентификация и авторизация

1. **Хеширование паролей** через bcrypt (через `passlib`)
2. **JWT-токены** с двумя видами:
   - Access token — короткий (15 минут)
   - Refresh token — долгий (30 дней), хранится в БД, ротация при использовании
3. **Автообновление** access-токена через интерцептор Dio при HTTP 401
4. **Безопасное хранение** на устройстве через `flutter_secure_storage` (Keychain/Keystore)

### 10.2. Защита от атак

1. **Rate limiting** через `slowapi`:
   - Жёсткий лимит на эндпоинты `/auth/*` для защиты от брутфорса
2. **Защита от перебора OTP:**
   - Блокировка аккаунта после N неудачных попыток (`locked_until`, `failed_login_attempts`)
3. **SQL Injection:**
   - Использование ORM SQLAlchemy с параметризованными запросами
4. **Security headers** через middleware:
   - `X-Content-Type-Options: nosniff`
   - `X-Frame-Options: DENY`
   - `Referrer-Policy: strict-origin-when-cross-origin`
   - `Strict-Transport-Security` (только в production)
5. **CORS** настроен с белым списком доменов

### 10.3. Безопасность платежей

1. **Не храним платёжные карты**
2. **Не интегрируем напрямую банковский API** (на текущем этапе)
3. **Двойная проверка платежей:**
   - Банк показывает поступление средств
   - Администратор подтверждает зачисление, сверяя `payment_code`
4. **Атомарные транзакции** при списании с баланса (`SELECT FOR UPDATE`)
5. **Лимиты пополнения:** $10 - $1000 за одну заявку
6. **Логирование действий админа:** поле `admin_user_id` в каждой подтверждённой/отклонённой транзакции

### 10.4. Защита персональных данных

1. **Аналитика обезличена:** клиники видят только агрегированные цифры, не имена пациентов
2. **Отзывы:** только автор может удалить свой отзыв (или администратор по жалобе)
3. **Локальное хранение избранного** для пациентов (без обязательной авторизации)

- Веб-страница в админ-панели для подтверждения заявок
- Заглушка под webhook Mbank API (Strategy pattern для будущей автоматизации)

### Этап 4: Автоматизация (планируется) ⏳
- **Celery beat** для периодических задач
- Напоминания о продлении за 7/3/1 день до окончания подписки
- Автодеактивация «лишних» врачей при истечении подписки
- Авто-отмена просроченных заявок на пополнение (TTL 7 дней)
- Авто-предупреждение клиник при N жалобах за период

### Этап 5: Интеграции (после получения юр.лица) ⏳
- Реальная интеграция Mbank Business API

Проект **MedFind** представляет собой полноценную медицинскую платформу с реалистичной бизнес-моделью и проработанной архитектурой. На текущий момент реализован основной функционал MVP, система монетизации через подписки и личные счета, аналитика для премиум-клиентов и веб-панель администратора.

Особое внимание уделено:

1. **Безопасности** — bcrypt для паролей, JWT с ротацией, rate limiting, атомарные финансовые операции

4. **Пользовательскому опыту** — единая дизайн-система, анимации, многоязычность
5. **Бизнес-обоснованности** — B2B2C модель, обеспечивающая монетизацию без затрат для конечного пользователя

Проект готов к публичному запуску после регистрации юридического лица и подключения банковского API для автоматизации платежей.
