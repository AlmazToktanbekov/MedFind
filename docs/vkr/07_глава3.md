# ГЛАВА 3. ТЕСТИРОВАНИЕ И ВНЕДРЕНИЕ СИСТЕМЫ

## 3.1. Тестирование разработанной системы

### 3.1.1. Цели, уровни и методика тестирования

Тестирование является обязательным этапом разработки программного обеспечения, предшествующим вводу системы в эксплуатацию [6]. Целью тестирования разработанной системы «MedFind» являлась проверка её соответствия функциональным и нефункциональным требованиям, сформулированным в первой главе, а также выявление и последующее устранение ошибок. Тестирование охватывало все три компонента системы — серверную часть, мобильное приложение и веб-панель администратора.

Тестирование проводилось на нескольких уровнях. На уровне отдельных модулей проверялась корректность работы изолированных компонентов серверной части. На уровне интеграции проверялось совместное функционирование компонентов — взаимодействие мобильного приложения с серверным программным интерфейсом и обращение сервера к базе данных. На системном уровне проверялась работа приложения в целом при выполнении сквозных пользовательских сценариев.

В соответствии с указанными уровнями применялись следующие виды тестирования: функциональное тестирование по сценариям использования; тестирование программного интерфейса REST API; автоматизированное модульное тестирование серверной части; тестирование пользовательского интерфейса мобильного приложения на устройствах. Сочетание перечисленных видов позволило проверить как отдельные модули, так и систему в целом, и обеспечить достаточную полноту проверки в условиях разработки приложения одним исполнителем.

### 3.1.2. Функциональное тестирование

Функциональное тестирование проводилось методом «чёрного ящика»: проверялось соответствие фактического поведения системы ожидаемому при выполнении типовых пользовательских сценариев, без обращения к внутренней реализации. Сценарии формировались на основе функциональных требований и охватывали все роли пользователей — пациента, врача, клинику, аптеку и администратора. Для каждого сценария определялись исходные условия, последовательность выполняемых действий и ожидаемый результат, после чего фактический результат сопоставлялся с ожидаемым. Все выявленные несоответствия были проанализированы и устранены, после чего соответствующие сценарии тестировались повторно.

### 3.1.3. Тестирование программного интерфейса REST API

Для тестирования серверного программного интерфейса использовалась интерактивная документация, автоматически формируемая фреймворком FastAPI по спецификации OpenAPI и доступная в виде веб-страницы. Документация позволяет вызывать любой эндпоинт непосредственно из браузера, передавая параметры и просматривая ответ сервера, что делает её удобным инструментом ручного тестирования API без применения сторонних программ. Внешний вид интерактивной документации приведён на рисунке 3.1.

[РИСУНОК 3.1 — Интерактивная документация REST API (Swagger UI): перечень эндпоинтов системы, сгруппированных по маршрутизаторам, и форма вызова эндпоинта]

В ходе тестирования API проверялись несколько аспектов. Во-первых, корректность кодов состояния HTTP: успешные операции должны возвращать коды группы 2xx, а ошибочные запросы — соответствующие коды группы 4xx. Во-вторых, работа валидации входных данных схемами Pydantic: при передаче данных некорректного типа или с нарушением ограничений сервер должен отклонять запрос с кодом ошибки валидации. В-третьих, правильность разграничения доступа: выполнение защищённого эндпоинта без маркера доступа должно отклоняться с кодом 401, а при недостаточной роли пользователя — с кодом 403. Тестирование подтвердило, что программный интерфейс возвращает предсказуемые ответы, корректно обрабатывает некорректные запросы и не допускает выполнения операций без необходимых прав.

### 3.1.4. Автоматизированное тестирование

Для серверной части реализованы автоматизированные тесты с использованием фреймворка pytest. Автоматизированные тесты позволяют многократно и быстро проверять корректность работы кода после внесения изменений, что снижает риск появления новых ошибок при доработке системы. Тестами покрыт модуль обработки жалоб как наиболее критичный с точки зрения автоматических действий системы: проверяется подача жалобы, корректность агрегирования жалоб по объектам и срабатывание пороговых правил, приводящих к отправке уведомлений и автоматической блокировке нарушителя. Результат прогона автоматизированных тестов приведён на рисунке 3.2.

Остальные модули системы проверялись преимущественно функциональным тестированием и тестированием программного интерфейса. Расширение покрытия серверной части автоматизированными тестами отнесено к направлениям дальнейшего развития системы.

Поскольку приложение является кроссплатформенным и предназначено для широкого круга пользователей, важно убедиться в его корректном отображении и работе на устройствах с различными параметрами. Проверялись адаптивность интерфейса при разных размерах экрана, корректность работы на различных версиях операционной системы, правильность отображения при смене языка интерфейса. ### 3.1.6. Тестирование безопасности

Отдельное внимание при тестировании уделялось проверке мер безопасности, реализованных в системе и описанных во второй главе. Проверялось, что пароли пользователей не хранятся в базе данных в открытом виде, а сохраняются исключительно в виде криптографических хешей. Проверялась работа защиты от подбора пароля: после нескольких неудачных попыток входа подряд учётная запись временно блокировалась, исключая дальнейший перебор. Проверялось ограничение частоты запросов — при превышении допустимого числа обращений за короткий промежуток времени сервер отклонял избыточные запросы. Проверялось разграничение доступа: попытки выполнения защищённых операций без аутентификации или с недостаточной для операции ролью отклонялись сервером с соответствующими кодами ошибок. Проверялось наличие в ответах сервера защитных HTTP-заголовков. Результаты тестирования безопасности подтвердили, что заложенные механизмы защиты функционируют в соответствии с проектными решениями и обеспечивают защиту данных пользователей.

### 3.1.7. Отладка

В процессе разработки и тестирования для поиска и устранения ошибок применялись встроенные средства отладки. На стороне мобильного приложения использовался компонент логирования HTTP-запросов, выводящий в консоль разработчика полные сведения о каждом запросе и ответе сервера, что позволяло быстро локализовать ошибки сетевого взаимодействия. На стороне сервера применялось журналирование, а специальный режим разработки давал возможность получать коды подтверждения непосредственно в ответе сервера без реальной отправки SMS, что существенно ускоряло отладку сценариев аутентификации. Совокупность этих средств обеспечила эффективное выявление и устранение ошибок на всех этапах разработки.

## 3.2. Развёртывание и сопровождение системы

### 3.2.1. Требования к программному окружению

Для развёртывания серверной части системы требуется среда выполнения языка Python и система управления базами данных PostgreSQL. Серверное приложение запускается ASGI-сервером Uvicorn. Серверная часть не предъявляет высоких требований к аппаратному обеспечению и может быть развёрнута как на физическом сервере, так и в облачной инфраструктуре.

Мобильное приложение собирается средствами инструментария Flutter в установочный пакет для операционной системы Android и в приложение для операционной системы iOS из единой кодовой базы. Для работы приложения на устройстве пользователя требуется подключение к сети Интернет, за исключением раздела «Первая помощь», доступного офлайн. Веб-панель администратора не требует установки и открывается в браузере на персональном компьютере.

### 3.2.3. Порядок развёртывания

Развёртывание серверной части включает следующие шаги: установку зависимостей; настройку файла конфигурации в соответствии с таблицей 3.3; применение миграций базы данных средствами инструмента Alembic для создания структуры таблиц; при необходимости — заполнение базы начальными данными; запуск сервера. После запуска сервер предоставляет программный интерфейс REST API, интерактивную документацию и веб-панель администратора, а также раздаёт загруженные пользователями изображения. Веб-панель администратора, через которую осуществляется эксплуатация и сопровождение платформы, показана на рисунке 3.3.

Для ввода системы в промышленную эксплуатацию необходимо подключить реальные внешние службы: SMS-шлюз Nikita.kg для отправки кодов подтверждения, службу Firebase Cloud Messaging для доставки push-уведомлений и сервис Mistral AI для работы AI-ассистента. ### 3.2.4. Сопровождение системы

Сопровождение разработанной системы поддерживается рядом встроенных средств. Журнал действий администраторов, журнал поисковых запросов и события аналитики дают объективные сведения о работе платформы и поведении пользователей, что позволяет своевременно выявлять проблемы. Регламентные задачи планировщика — анализ накопленных жалоб и снятие истёкших блокировок — выполняются автоматически по расписанию и не требуют участия персонала. Управление структурой базы данных при дальнейшем развитии системы выполняется через миграции, что обеспечивает согласованное, версионируемое и обратимое изменение схемы. Обновление справочного раздела «Первая помощь» выполняется вместе с обновлением мобильного приложения. Слоистая организация кода серверной части и разделение мобильного приложения на независимые функциональные модули упрощают внесение изменений и исправление ошибок в процессе сопровождения [9], поскольку изменение одного модуля не затрагивает остальные.

## 3.3. Планируемый эффект от внедрения

Поскольку приложение «MedFind» является бесплатным для всех категорий пользователей и не предусматривает монетизации, эффект от его внедрения носит не коммерческий, а социальный и временной характер. Планируемый эффект рассматривается отдельно для каждой группы участников.

**Эффект для пациентов.** Основной эффект состоит в существенном сокращении времени и трудозатрат на поиск медицинской услуги. При существующих способах поиска, рассмотренных в первой главе, пациент вынужден последовательно просматривать социальные сети и картографические сервисы, вступать в переписку с врачами для выяснения стоимости и графика приёма, а также самостоятельно сопоставлять разрозненные и несравнимые между собой сведения. В системе «MedFind» все необходимые данные представлены в структурированном и сравнимом виде в едином приложении. Сопоставление трудозатрат пациента при двух подходах приведено в таблице 3.4.

| Ориентировочные затраты времени | от нескольких часов до суток | несколько минут |

Даже при умеренной оценке экономии в один–два часа на одно обращение и активной аудитории в несколько тысяч пользователей совокупная экономия времени населения составляет тысячи человеко-часов ежемесячно. Дополнительный социальный эффект для пациентов обеспечивает раздел «Первая помощь», доступный без подключения к сети и способный оказать информационную поддержку в экстренной ситуации, когда время оказания помощи имеет критическое значение.

Для иллюстрации совокупного эффекта приведём ориентировочную оценку. Примем, что среднее время поиска подходящего врача традиционными способами составляет около двух часов, а с использованием приложения «MedFind» — около десяти минут; таким образом, экономия времени на одно обращение составляет примерно 1,8 часа. При активной аудитории в 3000 пользователей и среднем числе обращений к поиску один раз в месяц совокупная экономия времени составит около 3000 × 1,8 ≈ 5400 человеко-часов ежемесячно. Приведённая оценка является ориентировочной и опирается на сравнительный анализ способов поиска из первой главы; однако даже при значительном изменении исходных допущений совокупный эффект остаётся существенным. Следует отметить, что по мере роста числа пользователей и наполнения каталогов величина эффекта возрастает.

**Эффект для врачей, клиник и аптек.** Поставщики медицинских услуг получают бесплатный канал цифрового присутствия с единообразным и структурированным представлением информации, что особенно значимо для начинающих специалистов и небольших учреждений, не имеющих собственных средств продвижения. Клиники получают инструмент управления составом своих врачей, а также обезличенную аналитику посещаемости профилей, позволяющую оценивать востребованность отдельных специалистов и направлений. Аптеки получают возможность информировать пациентов о расположении, режиме работы и контактах своих филиалов.

**Эффект для системы здравоохранения.** На уровне отрасли внедрение системы способствует повышению доступности и прозрачности рынка медицинских услуг, упрощает для населения получение медицинской помощи и формирует обезличенные данные о спросе — наиболее востребованных специализациях и частых поисковых запросах, — которые могут быть полезны при анализе потребностей населения в медицинских услугах. ## 3.4. Оценка эргономичности

Эргономичность разработанного приложения обеспечивается рядом конкретных проектных решений, направленных на удобство, понятность и снижение усилий пользователя при работе с системой. Эргономические требования учитывались на всех этапах проектирования, а не рассматривались как формальность.

**Единообразие интерфейса.** Все экраны приложения построены на основе единой дизайн-системы с фиксированными цветами, шрифтами и набором переиспользуемых компонентов. Благодаря этому пользователь, освоив один экран, легко ориентируется на остальных, поскольку одинаковые элементы выглядят и ведут себя одинаково на всех экранах приложения.

**Минимизация числа действий.** Структура навигации построена так, чтобы основные функции были доступны за минимальное число нажатий: нижняя панель навигации обеспечивает прямой доступ к четырём ключевым разделам с любого экрана приложения. Подбор врача по симптому избавляет пациента от необходимости самостоятельно определять нужную медицинскую специализацию — пользователь указывает беспокоящий его симптом на привычном языке, а сопоставление со специализацией выполняет система. Это особенно важно, поскольку пациент, как правило, не обладает медицинскими знаниями.

**Снижение усилий при типовых операциях.** Контактные действия реализованы через механизм глубоких ссылок: звонок врачу, переход в мессенджер и построение маршрута до учреждения выполняются одним нажатием, без ручного копирования номеров телефонов и адресов. Это снижает вероятность ошибки и ускоряет взаимодействие.

**Информативная обратная связь.** Приложение постоянно информирует пользователя о своём состоянии: при загрузке данных отображаются анимированные заполнители, имитирующие структуру содержимого; действия сопровождаются плавными анимациями переходов; ошибки и пустые результаты сопровождаются понятными поясняющими сообщениями. Благодаря этому пользователь всегда понимает, что система обрабатывает его запрос, и не воспринимает задержку как сбой.

**Доступность интерфейса.** Кнопки и интерактивные элементы имеют достаточный размер для уверенного нажатия пальцем, а контрастная цветовая палитра обеспечивает читаемость текста в различных условиях освещения. Раздел «Первая помощь» сознательно сделан доступным без подключения к сети — в экстренной ситуации пользователь получает инструкции независимо от наличия интернета.

**Поддержка родного языка.** Локализация интерфейса на русский, кыргызский и английский языки позволяет каждому пользователю работать с приложением на удобном ему языке. Для медицинского сервиса это имеет особое значение, поскольку точность понимания информации напрямую влияет на качество принимаемых пользователем решений.

**Предотвращение ошибок пользователя.** Необратимые и значимые действия — такие как удаление данных или отправка заявки — сопровождаются запросом подтверждения, что предотвращает их случайное выполнение. Формы ввода проверяют корректность введённых данных до отправки на сервер и указывают на ошибки непосредственно у соответствующих полей, что помогает пользователю быстро исправить неточность.

**Сохранение контекста работы.** История диалогов с AI-ассистентом и список избранного хранятся на сервере и привязаны к учётной записи пользователя, поэтому накопленные данные не теряются при смене устройства или переустановке приложения. Пользователь продолжает работу с того состояния, на котором остановился.

Перечисленные решения свидетельствуют о том, что разработанное приложение отвечает эргономическим требованиям и обеспечивает комфортную работу различных категорий пользователей.

## 3.5. Направления дальнейшего развития системы

Разработанная система «MedFind» представляет собой законченное и работоспособное решение, однако обладает потенциалом для дальнейшего развития. К основным техническим направлениям совершенствования системы относятся следующие. Расширение покрытия серверной части автоматизированными тестами повысит надёжность системы при её дальнейшей доработке. Перенос хранения загружаемых изображений из локальной папки сервера в облачное объектное хранилище повысит масштабируемость и отказоустойчивость. Формирование полного набора миграций базы данных упорядочит управление изменениями её структуры. Подключение реальных внешних служб — SMS-шлюза, службы push-уведомлений и сервиса искусственного интеллекта — необходимо для промышленной эксплуатации, и архитектура системы, как было показано выше, к этому подготовлена.

К функциональным направлениям развития относятся расширение аналитики платформы в веб-панели администратора, добавление возможности онлайн-записи на приём к врачу непосредственно в приложении, а также развитие функций AI-ассистента. Перечисленные направления не являются обязательными для текущей версии системы, которая полностью решает поставленные задачи, но определяют перспективу её дальнейшего совершенствования и адаптации к растущим потребностям пользователей.
